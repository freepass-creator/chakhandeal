## 1. 무엇을 만드는가 — «모두싸인 + 이행 이력»

착한거래가 **전자계약 서비스**가 된다. 계약서 템플릿을 여러 개 두고, 회원사가 그중 하나로 계약을
발행하고, 손님이 서명한다. **여기까지는 모두싸인과 같다.**

**다른 것은 그다음이다. 그 계약을 어기면 이력으로 등록된다.**

```
계약 체결(착한거래)  →  이행 기간  →  불이행 발생
                                        ↓
                              위반 등록 — **그 계약을 근거로**
                                        ↓
                        본인 이력에 쌓임 → 다음 거래 상대가 본인 제출로 확인
```

이 고리가 착한거래를 모두싸인과 가르는 지점이다. 서명은 수단이고 **목적은 이행 기록**이다.
그리고 이건 착한거래에 이미 있는 것(`risks` 위반 등록·검증 링크)과 **같은 축**이다 —
전자계약은 그 위반 등록에 **근거를 붙여 주는** 기능이다.

### 지금 위반 등록의 약점

현재 `lib/server/risks.js` 의 등록은 회사가 `type`·`evidence`(자유 텍스트)를 넣는 구조다.
근거가 회사 주장뿐이라 이의제기가 들어오면 다툴 수밖에 없다.

계약이 붙으면 달라진다.

| | 지금 | 전자계약 연동 후 |
|---|---|---|
| 근거 | 회사가 쓴 `evidence` 텍스트 | **본인이 서명한 계약서의 특정 조항** |
| 신원 | 이름+생년 matchKey | **본인확인(신분증·셀피)을 거친 서명자** |
| 다툼 | 회사 주장 vs 본인 주장 | 서명 시점·문서 해시가 봉인돼 있음 |

**이게 프리패스가 원하는 진짜 이유다.** 저신용·무심사 렌터카라 미납·잠적 위험이 크고,
계약 근거가 있는 이력이 다음 거래의 심사 자료가 된다.

## 2. doctrine — 계약서는 «2차 전달물»이 아니다

`docs/platform-principles.md` §"왜 증명서가 아닌가" 를 다시 읽으면 금지 대상이 명확하다.

> **2차 전달물**은 검증 링크만 허용한다. 파일·캡처·복사 문구·PDF 는 위조·재배포가 쉽다.

여기서 말하는 2차 전달물은 **«이용자가 자기 신뢰를 상대에게 증명하는 산출물»** — 즉 증명서다.
**계약서는 그 범주가 아니다.** 계약서는 증명 산출물이 아니라 거래 당사자 간 문서다.

따라서 착한거래가 계약서 템플릿을 보관하고 서명본을 보관하는 것은 **원칙 위반이 아니다.**
지켜야 할 선은 이것뿐이다.

- 계약서·서명본은 **당사자(본인·해당 회원사)만** 접근한다.
- **증명서에는 계약서를 넣지 않는다.** 제3자에게 나가는 것은 여전히 검증 링크이고,
  링크가 보여주는 것은 「본인확인 완료 · 계약 N건 · 확정 위반 N건」 같은 **사실 요약**이다.
- 계약서 원문을 증명 수단으로 카톡·메일에 첨부하지 않는다.

렌탈 버티컬 고도화 방향("조회·문서 복사 → 본인 검증 링크 전달")과도 어긋나지 않는다 —
바뀌는 것은 «증명» 경로가 아니라 «계약 체결» 경로다.

## 3. 지금은 받을 수 없다 — 선행 조건

`docs/SECURITY-DESIGN.md` D2:

> 본인확인은 당장 스텁 유지 … **실데이터 오픈은 실 IdV 전까지 보류**(데모는 계속).

프리패스 계약에는 **주민등록번호**가 들어간다. 본인확인이 mock 인 상태로 그걸 받으면 안 된다.
따라서 순서는 이렇다.

```
지금        프리패스는 자체 서명으로 B2B 오픈 (착한거래 대기)
Phase 4~6   consent_grant 열람권한 · 불변감사 · 관리자 마스킹/2인승인
+ D2        **실 IdV 도입** (PASS/통신사 · 얼굴매칭 엔진)
그 다음     프리패스 서명 경로 전환
```

프리패스 쪽은 오픈 전에 **필드 예약만** 해 뒀다(`esign_provider`·`esign_id`·`esign_verify_url`·
`esign_seal_hash`). 그쪽 출시 Rules 가 계약 필드를 불변으로 잠그기 때문에 나중에 추가할 수 없어서다.
즉 **착한거래가 준비되면 회원사 쪽은 어댑터 교체 수준**으로 붙는다.

## 5. 범위 — 계약서는 착한거래가 «가진다»

사장님 방향(2026-08-04): 착한거래가 **렌트사별 커스터마이징 계약서**를 만들어 주거나
**표준계약서**를 쓰게 하고, **예약시스템까지** 간다. 회원사는 그 템플릿으로 **자기 화면에서 발송**한다.

즉 문서의 주인이 바뀐다.

| | 초기 구상(2026-07-31) | **확정 방향(2026-08-04)** |
|---|---|---|
| 계약서 템플릿 | 회원사가 보유 | **착한거래가 보유·관리**(표준 + 렌트사별 커스텀) |
| 계약서 렌더 | 회원사가 만들고 해시만 전달 | **착한거래가 데이터로 렌더** |
| 회원사가 보내는 것 | 문서 해시 | **템플릿ID + 계약 데이터** |
| 발송 | 회원사 | 회원사 화면에서 «발송» → 착한거래가 실제 발송 |

이게 더 낫다 — 계약서 문구·법적 정합·버전 관리가 **한 곳에 모인다.** 회원사마다 제각각
템플릿을 들고 있으면 조항이 갈라지고, 위반 등록의 근거로 쓸 수가 없다.

## 6. 인터페이스(초안)

```
① 템플릿 목록   GET /api/v1/contract/templates?memberCompany=freepass
   → [{ templateId, name, version, kind: 'standard'|'custom', fields:[…] }]
   ※ 표준계약서 + 그 회원사 전용 커스텀. 회원사는 자기 것 + 표준만 본다(교차 노출 금지).

② 계약 발행     POST /api/v1/contract/issue        Authorization: ApiKey <회원사 키>
   { templateId, externalRef,                       // externalRef = 회원사 계약키
     signer: { name, birth, phone },
     data: { 차량번호, 차종, 기간, 월대여료, 보증금, 인수·반납 조건 … } }
   → { contractId, signUrl, previewUrl, expiresAt }
   ※ 착한거래가 템플릿에 data 를 채워 계약서를 만든다. 회원사는 렌더링을 하지 않는다.

③ 발송          POST /api/v1/contract/{contractId}/send   { channel: 'kakao'|'sms' }
   ※ 회원사 화면의 «발송» 버튼이 이걸 부른다. 회원사가 signUrl 을 직접 보내도 된다.

④ 손님 여정     signUrl → 본인확인(신분증·OCR·셀피) → 계약서 확인 → 서명

⑤ 완료 통보     POST <회원사 웹훅>        X-Chakhandeal-Signature: HMAC-SHA256
   { contractId, externalRef, status: signed|rejected|expired,
     signedAt, verifyUrl, sealHash, obligationId }
   ※ obligationId = 이 계약으로 생긴 **이행 대상**. 위반 등록이 이걸 참조한다(§1).

⑥ 위반 등록     POST /api/v1/obligation/{obligationId}/breach
   { type, occurredAt, note }
   → 이력에 «계약 근거 있는» 위반으로 기록. 자유 텍스트 evidence 와 등급이 다르다.
```

**회원사가 보내는 PII 는 `name`·`birth`·`phone` 뿐이다.**
주민등록번호·주소·면허번호는 착한거래가 본인확인 과정에서 **직접** 받는다 — 회원사를 거치지 않는다.
회원사의 PII 보관 면적이 줄어드는 게 이 연동의 부수 이득이다.

## 7. 예약시스템과의 관계

예약까지 착한거래가 가면 순서가 이렇게 된다.

```
예약(착한거래) → 계약 발행·서명(착한거래) → 이행 기간 → 이행/불이행 등록(착한거래)
                        ↑
              회원사(프리패스)는 매물·요금·정산을 갖고
              «어떤 차를 얼마에» 를 데이터로 넘긴다
```

**경계를 흐리지 말 것**: 매물·재고·요금·정산은 회원사 몫이고, 신원·문서·이행 기록은 착한거래 몫이다.
예약을 착한거래가 받더라도 **재고 판단은 회원사에 물어야** 한다(예약 가능 여부 조회 API가 별도로 필요).
이건 이번 요청 범위 밖이지만 설계 시 자리를 남겨 둘 것.

## 8. 보안 불변식과의 정합 (SECURITY-DESIGN)

- **불변식 2(교차검색 금지)**: 회원사는 「이 사람 다른 회사 계약 있나」를 물을 수 없다.
  조회는 자기가 만든 `contractId`/`externalRef` 로만.
  **템플릿 목록도 마찬가지다** — 회원사는 표준 + 자기 커스텀만 본다. 타사 커스텀 계약서가
  목록에 보이면 그 자체로 영업 정보 유출이다.
- **불변식 3(회사별 가명토큰)**: 같은 손님도 회원사마다 `company_user_token` 이 다르다.
  이 연동이 그 격리를 우회하는 통로가 되면 안 된다.
- **불변식 5(본인 제출 모델)**: 착한거래에 쌓인 이력을 회원사가 **당겨오는 게 아니라**,
  본인이 회원사에 **제출**하는 방향이다. 프리패스가 심사에 쓰려면 그 흐름(Phase 4 consent_grant)을 타야 한다.
  — 서명 연동과 이력 제출은 **별개 기능**이다. 섞지 말 것.
- **불변식 8(관리자도 원문 자유조회 불가)**: 회원사 API Key 가 이 제한을 넘지 않는다.

## 9. 정리

- 방향·doctrine 해소는 확정됐다. **막고 있는 것은 실 IdV(D2) 하나**다.
- 2026-08-04 로 범위가 커졌다 — 서명 대행이 아니라 **계약서 템플릿·발행·예약까지 가는 서비스**다.
  Phase 4 이후 순서를 잡을 때 이 규모로 계획할 것(§5~7).
- Phase 4 브리프가 이미 나와 있으므로(`docs/PHASE4-BRIEF.md`) 그 뒤 순서에 이 서비스를 얹으면 된다.
- 회원사(프리패스)는 대기 중이고, 붙일 준비(필드 예약)는 끝났다.
- 구현은 Cursor, 설계·게이트는 Claude — 기존 파이프라인 그대로.
