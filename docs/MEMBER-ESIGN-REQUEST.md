## 1. 누가, 무엇을 원하나

**프리패스(freepasserp4)** — 저신용·무심사 렌터카 3자 마켓 ERP.
현재 자체 전자서명이 돌고 있다(손님에게 링크 발송 → 주민등록번호·면허번호·주소 수집 → 서명 이미지 → 승인).
이걸 **착한거래로 옮기고 싶다.**

원하는 것은 넷이다.

1. 본인확인(신분증 촬영 + OCR + 셀피)
2. 서명 수집
3. 문서 해시 + 타임스탬프 봉인
4. `/v?id=` 검증 링크 발급

**원하지 않는 것**: 계약서 파일 보관·배포. 원문은 회원사가 갖는다.

## 2. doctrine 과 충돌하지 않는다

`docs/platform-principles.md` 는 **«PDF·파일 증명 금지, 2차 전달물은 검증 링크만»** 을 못박는다.
계약서 PDF 를 착한거래가 다루면 정면 충돌이다.

**해소**: 착한거래는 파일을 받지도 배포하지도 않는다. 받는 것은 **문서 해시**뿐이고,
내보내는 것은 **"이 해시의 문서를 이 사람이 언제 서명했다"** 는 검증 링크뿐이다.
파일이 아니라 사실을 증명한다 — 원칙 위반이 아니라 원칙 그대로다.

렌탈 버티컬의 고도화 방향("조회·문서 복사 → 본인 검증 링크 전달")과도 같은 방향이다.

## 3. 지금은 받을 수 없다 — 선행 조건

`docs/SECURITY-DESIGN.md` D2:

> 본인확인은 당장 스텁 유지 … **실데이터 오픈은 실 IdV 전까지 보류**(데모는 계속).

프리패스 계약에는 **주민등록번호**가 들어간다. 본인확인이 mock 인 상태로 그걸 받으면 안 된다.
따라서 순서는 이렇다.

```
지금        프리패스는 자체 서명으로 B2B 오픈 (착한거래 대기)
Phase 4~6   consent_grant 열람권한 · 불변감사 · 관리자 마스킹/2인승인
+ D2        **실 IdV 도입** (PASS/통신사 · 얼굴매칭 엔진)
그 다음     프리패스 서명 경로 전환
```

프리패스 쪽은 오픈 전에 **필드 예약만** 해 뒀다(`esign_provider`·`esign_id`·`esign_verify_url`·
`esign_seal_hash`). 그쪽 출시 Rules 가 계약 필드를 불변으로 잠그기 때문에 나중에 추가할 수 없어서다.
즉 **착한거래가 준비되면 회원사 쪽은 어댑터 교체 수준**으로 붙는다.

## 4. 착한거래에 신설이 필요한 것

2026-07-31 조사 기준. 현재 코드에 없는 것들이다.

| 항목 | 현재 | 필요 |
|---|---|---|
| 서명요청 생성 API | 없음 — 손님이 4자리 코드 직접 입력 전제 | `POST /api/v1/sign/request` → `{signId, signUrl}` |
| 서명 이미지 저장 | **없음** — `signed` 불리언만, PNG dataURL 을 버린다 | 증거로 보존 |
| 문서 해시·타임스탬프 봉인 | 없음 — 문서 개념 자체가 없고 PDF 라이브러리 0 | 해시 수신 + 봉인 시각 |
| 웹훅/콜백 | 없음(grep 0건) | 완료 통보 + HMAC 서명 |
| `externalRef` 상관 필드 | 없음 — 이름+생년 HMAC matchKey 뿐 | 회원사 계약키 보관 |
| M2M 인증 | 없음 — 사용자 토큰뿐 | 회원사 API Key |
| 실 본인확인 | mock (`DEMO_MODE` 기본 true) | D2 |

**하위호환**: 박제 URL `/consent?code=` · `/v?id=` 는 깨지 않는다.

## 5. 인터페이스(초안)

```
① 서명 요청   POST /api/v1/sign/request      Authorization: ApiKey <회원사 키>
   { documentHash, documentMeta, signer:{name, birth}, memberCompany, externalRef }
   → { signId, signUrl, expiresAt }

② 손님 여정   signUrl → 신분증 → OCR → 셀피 → 문서확인 → 서명

③ 완료 통보   POST <회원사 웹훅>             X-Chakhandeal-Signature: HMAC-SHA256
   { signId, externalRef, status: signed|rejected|expired, signedAt, verifyUrl, sealHash }
   ※ 웹훅 전에 폴링(GET /api/v1/sign/{signId})으로 시작해도 된다.
```

**회원사가 보내는 PII 는 `name`·`birth` 뿐이다.**
주민등록번호·주소·면허번호는 착한거래가 본인확인 과정에서 **직접** 받는다 — 회원사를 거치지 않는다.
회원사의 PII 보관 면적이 줄어드는 게 이 연동의 부수 이득이다.

## 6. 보안 불변식과의 정합 (SECURITY-DESIGN)

- **불변식 2(교차검색 금지)**: 회원사는 「이 사람 다른 회사 계약 있나」를 물을 수 없다.
  조회는 자기가 만든 `signId`/`externalRef` 로만.
- **불변식 3(회사별 가명토큰)**: 같은 손님도 회원사마다 `company_user_token` 이 다르다.
  이 연동이 그 격리를 우회하는 통로가 되면 안 된다.
- **불변식 5(본인 제출 모델)**: 착한거래에 쌓인 이력을 회원사가 **당겨오는 게 아니라**,
  본인이 회원사에 **제출**하는 방향이다. 프리패스가 심사에 쓰려면 그 흐름(Phase 4 consent_grant)을 타야 한다.
  — 서명 연동과 이력 제출은 **별개 기능**이다. 섞지 말 것.
- **불변식 8(관리자도 원문 자유조회 불가)**: 회원사 API Key 가 이 제한을 넘지 않는다.

## 7. 정리

- 방향·doctrine 해소는 확정됐다. **막고 있는 것은 실 IdV(D2) 하나**다.
- Phase 4 브리프가 이미 나와 있으므로(`docs/PHASE4-BRIEF.md`) 그 뒤 순서에 이 서비스를 얹으면 된다.
- 회원사(프리패스)는 대기 중이고, 붙일 준비(필드 예약)는 끝났다.
- 구현은 Cursor, 설계·게이트는 Claude — 기존 파이프라인 그대로.
